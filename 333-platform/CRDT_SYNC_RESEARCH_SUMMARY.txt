6 RESEARCH QUESTIONS ANSWERED
================================================================================

Q1: Sync Loop Design — Immediate vs Batched Send?
   ANSWER: Batched 20ms
   RATIONALE: 1.2 frame latency (imperceptible), 50-100x BW savings
   CODE: src/sync.rs, SyncManager::poll_and_send()

Q2: Delta Batching — How to Accumulate?
   ANSWER: VecDeque (in-memory) + optional IndexedDB persistence
   RATIONALE: <1μs per delta, O(deltas) space, optional durability
   CODE: src/sync.rs, SyncManager::delta_buffer

Q3: State Vector / Version Vector — How to Track Incremental Sync?
   ANSWER: HashMap<u32, u32> mapping peer_id → max_counter_seen
   RATIONALE: O(1) lookup, O(1) insert, scales to 1000+ peers
   ALGORITHM: Piggyback state_vector in every StateUpdate message
   CODE: src/sync.rs, SyncManager::state_vector + on_peer_sync()

Q4: Reconnection Sync — Full State vs Missing Deltas?
   ANSWER: Hybrid threshold at 1000 missing deltas
   RATIONALE: Cost crossover: 1000 × 50B deltas = 50KB vs 5MB full state
   DECISION: gap < 1000 → incremental; gap >= 1000 → full snapshot
   CODE: src/sync.rs, should_send_full_state()

Q5: Full State Snapshot — When to Send?
   ANSWER: On peer join + large reconnection gaps
   TRIGGERS:
     - New peer joins → send StateFull (0x02) immediately
     - Reconnect with gap >1000 → send StateFull
     - Normal operation → send StateUpdate (0x01) with deltas only
   COST: O(unique_keys) per snapshot, typically 100K blocks = 5MB

Q6: Ordering Guarantees — Do We Need Ordered DataChannel?
   ANSWER: Use reliable ordered channel, but LWW doesn't strictly require it
   REASON: Lamport timestamps guarantee convergence regardless of message order
   PROOF: Last-Writer-Wins semantics make order irrelevant (higher TS always wins)
   CONFIG: RTCDataChannel with ordered=true (standard, no overhead)

ARCHITECTURE SUMMARY
================================================================================

SYNC LOOP FLOW:
  1. User: place_block("0,0,0", "stone")
  2. CRDT: world.set(key, value) → LwwDelta
  3. QUEUE: sync_mgr.on_local_delta(delta) → VecDeque
  4. BATCH: Every 20ms, sync_mgr.poll_and_send() flushes
  5. ENCODE: wire::encode(StateUpdate, JSON payload)
  6. SEND: room.broadcast() → WebRTC DataChannel (Reliable, FIFO)
  7. NETWORK: ~5-20ms RTT
  8. RECEIVE: Peer decodes StateUpdate
  9. MERGE: world.merge_delta() × N deltas
 10. SV: Update state_vector[sender] = max(SV[sender], incoming_counter)
 11. CONVERGE: All peers reach same state (CRDT property)

STATE VECTOR ALGORITHM:
  State Vector = HashMap<peer_id, max_counter_seen>
  
  On receive payload from peer_i with payload.deltas and payload.state_vector:
    for delta in payload.deltas:
      world.merge_delta(delta)
    for (peer_j, counter_j) in payload.state_vector:
      state_vector[peer_j] = max(state_vector[peer_j], counter_j)
  
  Result: Every peer learns what every other peer has seen
  → Enables incremental sync: "send only deltas peer hasn't seen"

RECONNECTION LOGIC:
  Reconnecting peer sends: SV_peer = {P1:20, P2:15, P3:0}
  
  Server computes: missing = sum((SV_local[p] - SV_peer[p]) for all p)
  
  if missing < 1000:
    send incremental (StateUpdate with deltas)
  else:
    send full snapshot (StateFull with entire map)

CONVERGENCE PROOF:
  Concurrent writes: P1 writes stone (TS: 1:10), P2 writes dirt (TS: 2:5)
  
  Order A: [1:10, 2:5] → apply stone, skip dirt (5<10) → Final: stone ✓
  Order B: [2:5, 1:10] → apply dirt, overwrite stone (10>5) → Final: stone ✓
  
  Lamport(counter) + node_id(tiebreaker) = deterministic, order-independent convergence

MESSAGE TYPES (4 total)
================================================================================

StateUpdate (MsgType::StateUpdate = 0x01) — Regular sync
  Payload: JSON { deltas: [LwwDelta], state_vector: {...} }
  Frequency: Every 20ms when buffer non-empty
  Size: ~50 bytes per delta

StateFull (MsgType::StateFull = 0x02) — New peer or large gap
  Payload: JSON { entries: HashMap<K, (V, timestamp)> }
  Frequency: On peer join, or reconnect gap >1000
  Size: ~50 bytes × unique_keys (e.g., 5MB for 100K blocks)

================================================================================
KEY DESIGN DECISIONS
================================================================================

✅ BATCHED 20ms (not immediate)
   - Matches 60fps browser refresh (16.67ms frames)
   - 50-100x bandwidth savings vs immediate send
   - Imperceptible latency for collaborative apps

✅ VECDQUE (not persistent index)
   - Speed: <1μs per push/pop
   - Optional IndexedDB backup for durability
   - Simplicity: no database schema to manage

✅ HASHMAP<u32, u32> (not bloom filters)
   - O(1) lookup, O(1) insertion
   - Scales to 1000+ peers easily
   - Future: switch to bloom filters if >10K peers

✅ THRESHOLD 1000 (not fixed 500 or 2000)
   - 1000 deltas × 50B = 50KB
   - Full state ≈ 5MB (at 100K blocks)
   - Cost crossover point (incremental becomes cheaper)

✅ FULL STATE ON JOIN (not incremental always)
   - New peer has no deltas → send full snapshot
   - Simplest, most reliable approach
   - One-time cost acceptable

✅ RELIABLE ORDERED CHANNEL (not unreliable)
   - Simplicity: FIFO guarantees easier mental model
   - Efficiency: fewer out-of-order merge cases
   - Durability: auto-retransmit on loss
   - Standard: RTCDataChannel ordered=true is default

================================================================================
GOTCHAS & MITIGATIONS
================================================================================

Gotcha 1: State Vector Skew
  Problem: Peer claims to have seen 1000 ops but only has 900
  Mitigation: Store SV in durable log, verify with checksums

Gotcha 2: Memory Explosion
  Problem: Delta buffer grows unbounded if flush never runs
  Mitigation: Force flush if buffer > 1000 deltas (backpressure)

Gotcha 3: Ordering Assumption
  Problem: Code assumes FIFO, but unreliable channel drops packets
  Mitigation: Use Reliable ordered channel (configured in DataChannel)

Gotcha 4: Convergence Delay
  Problem: User expects instant, but we batch 20ms
  Mitigation: 20ms imperceptible at 60fps; set expectations

Gotcha 5: Full State Size
  Problem: 100K blocks × 50B = 5MB takes seconds to send
  Mitigation: Only send on join/large gap; compress if needed later
