7 KEY QUESTIONS ANSWERED
================================================================================

Q1: Can Playwright open two browser contexts that connect via WebRTC?
A:  YES. Playwright natively supports multiple isolated contexts within one test.
    Use separate contexts for true P2P simulation (not just pages).
    Architecture: Browser → Context A (Peer1) + Context B (Peer2)
    Source: Playwright docs on browser contexts

Q2: How to handle ICE candidates and STUN in Playwright test environment?
A:  THREE approaches (in order):
    A) Real STUN servers (RECOMMENDED) — browser gathers candidates naturally
    B) Override STUN for host-only (fastest, localhost-only)
    C) Mock ICE entirely (not realistic, avoid)
    
    Recommendation: Use approach A (real STUN). Localhost works fine.
    STUN latency ~50-100ms is negligible for P2P tests.

Q3: Mock vs real signaling server — which approach?
A:  ALWAYS use REAL signaling server (ws://localhost:8333).
    Why: Your server is minimal (91 lines, pure relay).
         Mocking adds complexity without benefit.
         Cost: negligible (1-5ms localhost latency).

Q4: Waiting strategies — how to wait for WebRTC connection?
A:  THREE patterns:
    A) DataChannel open (RECOMMENDED)
       - dataChannel.readyState === 'open'
       - Most reliable for CRDT/consensus
    
    B) Connection state
       - peerConnection.connectionState === 'connected'
       - Less reliable (DC not guaranteed open)
    
    C) ICE gathering complete (debugging only)
       - iceGatheringState === 'complete'
    
    RECOMMENDED timeout: 15 seconds (ICE gathering can take 5-10s first run)

Q5: Can Playwright intercept DataChannel messages?
A:  PARTIAL. Playwright cannot directly inspect binary DataChannel data.
    SOLUTION: Expose logging API from WASM
    
    In Rust: pub fn getReceivedMessages() -> Vec<String>
    In test: window.__testHarness.getMessages()
    
    Alternative: Verify state changes (convergence) instead of messages
    Not recommended: MockRTC library (adds dependency, overkill)

Q6: Existing Playwright WebRTC examples or libraries?
A:  Few official examples exist. Known libraries:
    - MockRTC (mock peer + interception)
    - WebRTC samples (reference implementations)
    - Markaicode guide (CDP overrides for media/network)
    
    Recommendation for 333: Write custom test harness (100-200 lines)
    - Simpler than MockRTC integration
    - Specific to your use case (DataChannel only, no video/audio)

Q7: Alternatives: Puppeteer vs Cypress vs manual testing?

================================================================================
KEY DESIGN DECISIONS
================================================================================

Decision 1: Real signaling server (not mock)
Rationale: Simple relay, trivial to run locally, avoids mock complexity

Decision 2: Two separate browser contexts (not pages)
Rationale: True network isolation, simulates real P2P scenario authentically

Decision 3: Logging API in WASM (for message inspection)
Rationale: Playwright cannot intercept DataChannel directly

Decision 4: Wait for DataChannel open (not connection state)
Rationale: More reliable indicator of readiness for CRDT/consensus

Decision 5: Single worker (not parallel)
Rationale: Shared signaling server (simple relay, not parallel-safe)

Decision 6: 15 second timeout (for initial connection)
Rationale: ICE gathering can take 5-10s on first run, STUN adds latency

ARCHITECTURE
================================================================================

Test Process:
  Playwright Test Runner
    ├─ Creates browser instance (Chrome)
    │  ├─ Context A (Peer 1)
    │  │  └─ Page 1 → localhost:5173
    │  │     └─ WASM RTCPeerConnection
    │  │        └─ DataChannel (ordered, reliable)
    │  │
    │  └─ Context B (Peer 2)
    │     └─ Page 2 → localhost:5173
    │        └─ WASM RTCPeerConnection
    │           └─ DataChannel (ordered, reliable)
    │
    └─ Signaling Server (ws://localhost:8333)
       └─ Room relay → SDP/ICE exchange

Data Flow:
  1. Peer1 creates RTCPeerConnection (offerer)
  2. Peer1 creates offer SDP
  3. Peer1 sends offer → signaling server → Peer2
  4. Peer2 sets remote description (SDP from Peer1)
  5. Peer2 creates answer SDP
  6. Peer2 sends answer → signaling server → Peer1
  7. Both collect ICE candidates via STUN
  8. DataChannel established (ordered, reliable)
  9. Messages exchanged (CRDT deltas, consensus votes)
  10. Convergence verified (state matching)

================================================================================
KNOWN LIMITATIONS & WORKAROUNDS
================================================================================

Limitation 1: No direct DataChannel message inspection
Workaround: Expose logging API from WASM (30 lines of code)
Cost: Minimal (test-only code)
Benefit: Can verify message content + ordering

Limitation 2: No built-in packet loss simulation
Workaround: Use page.route() with setTimeout
Cost: More complex test code
Benefit: Can test reliability/retry logic

Limitation 3: No TURN server (only STUN)
Impact: Localhost only; won't work through NAT
Workaround: Use Playwright's network throttling for latency
Future: Add TURN server if needed for real-world testing

Limitation 4: No audio/video media
Impact: DataChannel-only (your use case)
Workaround: Use --use-fake-device-for-media-stream if added later
Reference: Markaicode guide for media mocking
